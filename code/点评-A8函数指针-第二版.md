## 二、但输出第 3 段不对（自检却是绿的）


**标题写"升序"，实际排的是降序。** 而且它跟第 4 段（desc = true）打出来**一模一样**——
两段结果相同，本身就说明"那个开关没起作用"。

对照你自己写的两行（第 107 / 114 行）：

```cpp
// 第 107 行（第一次：desc = false）
return desc ? p.score < q.score : p.score > q.score;   // ❌ 方向还是反的

// 第 114 行（第二次：desc = true）
return desc ? p.score > q.score : p.score < q.score;   // ✅ 这个你改对了
```

**改法**：第 107 行照第 114 行抄一遍（这两处本来就该是**同一个 lambda，一个字都不差**）：

```cpp
return desc ? p.score > q.score : p.score < q.score;
```

改完再跑，第 3 段应该变成 `60 → 70 → 70 → 95 → 95 → 95`（升序），第 4 段保持降序。

## 三、这一版真正该记住的：**自检绿了，不等于全对**

为什么自检没报错？去看那份自检代码最后一段（我没让你改的那块）：

```cpp
// TODO 4：最后一次 desc = true，所以 d 的分数应该是"非递增"
for (int i = 1; i < n; i++) {
    if (d[i - 1].score < d[i].score) { ok = false; ... }
}
```

它只检查 **`d` 的最终状态**——也就是**第二次排序之后**的顺序。
而第 3 段（desc = false 那一遍）排完就被第 4 段**覆盖**了，自检根本看不到它。

这不是我写错了，这是**测试本来就会有的盲区**，也是真实项目里最危险的 bug 类型：

> **测试全绿 + 功能是错的。** 因为测试只证明了"它检查过的那部分是绿的"，从来没证明"全都对"。

所以你这一版要拿走两条习惯：

1. **不要只看最后那行 `自检 ✅`** —— 要**逐段读输出**，尤其检查"每段标题"和"它下面打出来的东西"对不对得上。
   这次就是标题说升序、内容在降序，一眼就能看出来。
2. **测试覆盖不到的地方，靠人对需求的理解去补**。这个练习要求"同一个 lambda 用两遍、只改外面的开关"——
   既然要求两处一模一样，那**两段结果不一样才是对的**（一个升一个降）。两段一样，本身就是个信号。

> 附：这个自检的盲区算是**我设计的漏洞**——答对了"能不能编译"，但漏了"这一段对不对"。
> 下一轮我把练习的自检补强：在第一次排序后先存一份快照，让两段都各自被验一次。
